# Summary

Airflow 를 단일 서버에 깔아서 굴리던 시절을 지나서, 요즘은 **K8s 위에 Helm 으로 올리고, 매 태스크마다 리눅스 컨테이너 워커가 떴다 사라지는** 구조가 표준에 가까워졌어요. 이 시리즈에서는 이 구조를 처음부터 끝까지 정리합니다. 1편인 이 글은 그 전체 그림과 왜 이렇게 가는지를 잡아두고, 다음 편들에서 설치 → 워커 이미지 → 운영을 차례로 풀어요.

## 1. Airflow 가 뭐 하는 친구냐

`Airflow` 는 한 줄로 줄이면 **"스케줄러 + 워크플로우 매니저"** 예요. Python 으로 짠 `DAG`(Directed Acyclic Graph) 안에 태스크들을 정의해두면, 정해진 시간에 그 태스크들을 의존 관계에 맞춰 순서대로 실행해주고, 실패하면 재시도하고, 결과/로그/메트릭을 다 한곳에서 보여줘요.

데이터 파이프라인(ETL/ELT), 배치 잡, 주기적인 리포트 생성, ML 학습 트리거 같은 일에 폭넓게 씀.

핵심 컴포넌트는 4개로 정리할 수 있어요.

| 컴포넌트 | 역할 |
|---|---|
| `Webserver` | UI. DAG/태스크 상태 확인, 로그 보기 |
| `Scheduler` | 시간/의존성 보고 "이 태스크 지금 돌려야 한다" 결정 |
| `Worker` | 실제로 태스크 코드를 실행하는 일꾼 |
| `Metadata DB` | DAG 상태, 태스크 실행 이력, 사용자/권한 등 메타데이터 저장 |


<br>

## 2. 왜 K8s 위에 올리나?

Airflow 만 놓고 보면 굳이 K8s 가 필요한 도구는 아니에요. 한 대 서버에 깔아서도 충분히 굴러갑니다. 그럼 왜 K8s 로 가느냐?

가장 큰 이유는 **워커의 동적 스케일** 이에요. 데이터 파이프라인은 시간대마다 부하가 들쭉날쭉해요. 새벽 배치 시간에는 동시에 수십 ~ 수백 개 태스크가 떠야 하고, 낮에는 거의 놀아요. 고정된 워커 풀로 굴리면 새벽엔 모자라고 낮엔 자원이 놀아요.

K8s + `KubernetesExecutor` 조합은 이 문제를 깔끔하게 풀어요. **태스크 단위로 Pod 하나를 띄우고, 끝나면 바로 정리**. 부하 따라 자연스럽게 늘었다 줄었다 해요. 이런 점들도 같이 따라와요.

- 태스크끼리 환경 격리 (한 태스크의 라이브러리 버전이 다른 태스크에 영향 X)
- 자가복구 — Pod 가 죽으면 K8s 가 재시도, 노드가 죽어도 다른 노드로 옮김
- 리소스 한도(CPU/메모리)를 태스크 단위로 제한
- 기존 K8s 인프라(모니터링, 로깅, 시크릿) 그대로 재사용

> 💡 [[Docker_Kubernetes_워커_오케스트레이션]] 에서 정리한 "Docker 는 워커, K8s 는 오케스트레이터" 구도를 그대로 가져온다고 보면 돼요. Airflow 의 워커가 컨테이너로 추상화되고, 그걸 K8s 가 부립니다.


<br>

## 3. KubernetesExecutor 가 워커를 띄우는 그림

Airflow 에는 여러 종류의 Executor 가 있어요. 한 대 서버에서 쓰는 `LocalExecutor`, Celery 워커 풀을 쓰는 `CeleryExecutor`, 그리고 우리가 쓸 `KubernetesExecutor`.

`KubernetesExecutor` 의 동작을 한 그림으로 줄이면 이래요.

```text
[Scheduler Pod] ─── "이 태스크 돌려" ──▶ [K8s API]
                                          │
                                          ▼
                                  [새 Worker Pod 생성]
                                          │
                                          ▼  태스크 코드 실행 (DAG/Operator)
                                          │
                                          ▼  실행 끝 → Pod 자동 정리
```

핵심 포인트만 추리면 이래요.

- **워커 Pod 는 태스크 1개 = Pod 1개**. 끝나면 사라져요.
- 워커 Pod 의 이미지는 보통 **스케줄러/웹서버와 같은 Airflow 이미지** 를 씁니다 (그래야 DAG 코드를 같이 가져갈 수 있음).
- 워커 Pod 의 **스펙** (이미지, 리소스, 노드셀렉터, 볼륨, 시크릿, env) 은 `pod_template_file` 이라는 YAML 로 미리 정의해둠.
- 태스크 단위로 부분 override 도 가능 (`executor_config={"pod_override": ...}`).

> ✅ 그래서 "리눅스 이미지가 워커" 라는 말은 정확히는 "Airflow 가 미리 만들어둔 (또는 우리가 커스텀한) **리눅스 베이스 컨테이너 이미지** 가 매 태스크마다 새 Pod 로 떠서 워커 역할을 한다" 는 뜻이에요.

## 4. 왜 Helm 으로 올리나?

Airflow 를 K8s 에 올리려면 만들어야 하는 리소스가 한둘이 아니에요. `Deployment` 가 여러 개(webserver, scheduler, triggerer), `Service`, `Ingress`, `Secret`, `ConfigMap`, `ServiceAccount`, `Role`/`RoleBinding`, PVC, `StatefulSet`(Postgres/Redis 같이 깔 때) … 손으로 다 짜면 며칠 걸리고 변경 관리도 지옥이에요.

`Helm` 은 K8s 패키지 매니저예요. **공식 Helm 차트** 하나를 받아서 `values.yaml` 만 잘 채우면 위의 리소스들이 한꺼번에 생성/업데이트돼요.

| Helm 이 주는 것 | 설명 |
|---|---|
| 차트(템플릿 모음) | Airflow 가 필요로 하는 모든 K8s 리소스 정의 |
| `values.yaml` | 우리 환경에 맞춰 값만 바꿔서 주입 |
| `helm install` / `upgrade` | 한 방에 배포 / 업데이트 |
| 버전 관리 | 차트 버전 / 릴리스 이력을 K8s 안에 보관 |

Airflow 공식 Helm 차트는 `apache-airflow` repo 에 있고, 이게 사실상 표준이에요. 다음 편에서 이걸로 실제 설치를 합니다.

## 5. 시리즈 4편 로드맵

이 시리즈는 이렇게 굴러갑니다.

| 편 | 다룰 것 |
|---|---|
| (1/4) 개요 *(지금 글)* | 전체 그림, 왜 Helm + KubernetesExecutor 인가 |
| (2/4) 설치 | `helm repo add` → `values.yaml` → `helm install` 까지 셋업 한 호흡 |
| (3/4) 워커 이미지 | 커스텀 Airflow 이미지 빌드 + 레지스트리 + `pod_template_file` 로 워커 Pod 스펙 결정 |
| (4/4) 운영 | DAG 동기화(`git-sync`), 로그 영속화, 모니터링, 스케일, 트러블슈팅 |

## 6. 들어가기 전 사전 체크

본격적인 설치에 들어가기 전에 환경 체크 한 번 하고 가요.

- **K8s 클러스터** — `kind`, `minikube`, `Docker Desktop`, EKS/GKE 무엇이든 OK. `kubectl get nodes` 로 노드 1개 이상 `Ready` 상태면 됨.
- **kubectl** — 클러스터에 붙어 있어야 함.
- **Helm 3** — `helm version` 으로 3.x 확인.
- **컨테이너 레지스트리** — 워커 이미지를 푸시할 곳. Docker Hub, ECR, GHCR, GCR, 사내 Harbor 무엇이든.
- **(선택) Ingress 컨트롤러** — Airflow UI 를 외부에 노출할 거라면. 로컬 개발이면 `kubectl port-forward` 만 써도 충분.

리소스 기준은 워커 부하에 따라 천차만별이지만, **실험 목적이면 노드 1대에 4 vCPU / 8GiB RAM 정도** 면 첫 설치 + 가벼운 DAG 돌리는 데 무리 없어요.
