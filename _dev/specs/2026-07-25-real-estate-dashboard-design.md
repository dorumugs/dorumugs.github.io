# 부동산 실거래가 대시보드 — 설계

작성일: 2026-07-25
상태: 승인됨

## 목표

서울·경기 아파트 실거래가를 매일 누적 수집하고, 300세대 이상 단지를 대상으로 하는
정적 대시보드를 `/real-estate/` 에 운영한다.

## 범위

- 수집 대상: 서울 25개 자치구 + 경기 47개 시군구 = 72개 시군구
- 수집 기간: 2006-01 ~ 현재 (247개월)
- 총 백필 물량: 17,784콜 (거래 1,000건 초과 월의 추가 페이지 제외)
- 세대수 필터(300세대 이상)는 **수집이 아니라 집계 단계**에서 적용한다

## 아키텍처

```
[국토부 실거래가 API]  ──┐
  RTMSDataSvcAptTrade   │   scripts/collect_trades.py
  72 시군구 × 247개월    ├──▶  data/trades/YYYY/YYYY-MM.csv.gz   (원본 누적, 전량)
                        │
[odcloud 단지정보 API]  ──┘   scripts/collect_complexes.py
  AptIdInfoSvc            └──▶  data/complexes.csv.gz           (단지 마스터: pnu, 세대수)
                                        │
                                        ▼  scripts/build_dashboard.py
                                           (PNU 조인 + 300세대 필터)
                                _data/realestate/*.json          (집계본)
                                        │
                                        ▼
                                _pages/real-estate.md  →  /real-estate/
```

원본과 집계본을 분리하는 것이 핵심이다. 원본은 전량·불변으로 쌓고, 세대수 기준이나
지표 정의가 바뀌면 집계 단계만 다시 돌린다. 재수집은 발생하지 않는다.

## 구성 요소

### scripts/regions.py

72개 시군구 목록, 법정동 10자리 코드 테이블(PNU 조립용), 폐지/신설 구 대응 매핑을 제공한다.
법정동 코드 원본은 `data/region_codes_11_41.tsv` (서울·경기 subset, 약 2,700행).

의존성: 없음 (표준 라이브러리 + 동봉 TSV)

### scripts/collect_trades.py

(시군구 × 월) 격자를 순회하며 실거래가를 수집한다.

- 엔드포인트: `https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade`
- 파라미터: `serviceKey`, `LAWD_CD`, `DEAL_YMD`, `numOfRows=1000`, `pageNo`
- 인증키: `~/.claude.json` 의 real-estate MCP 서버 env `DATA_GO_KR_API_KEY` 에서 읽는다.
  **키는 저장소에 커밋하지 않는다.**

의존성: `regions.py`, 표준 라이브러리

### scripts/collect_complexes.py

odcloud `AptIdInfoSvc/getAptInfo` 로 서울·경기 단지의 `pnu` 와 `household_count` 를 수집해
`data/complexes.csv.gz` 로 저장한다.

`cond[PNU::LIKE]=<시군구 5자리>` 로 잘라 받는다. LIKE 는 부분일치라 '11680' 이 지번
자리에 들어간 타 시군구 단지가 딸려오므로, 받은 뒤 PNU 접두사로 다시 거른다.
`perPage` 상한은 1000.

실측: 72개 시군구 **187,208건**, 약 240콜. 이 중 300세대 이상은 5,139개 단지.

#### 매칭률 실측 (2026-07-25)

| 월 | 거래 건수 | PNU 조립 | 마스터 매칭 | 300세대+ 비중 |
|---|---|---|---|---|
| 2006-01 | 9,947 | 100.00% | 93.65% | 78.32% |
| 2011-06 | 12,930 | 100.00% | 94.15% | 75.01% |
| 2016-11 | 17,282 | 99.98% | 93.45% | 72.49% |

미매칭 약 6% 는 예상대로 여러 지번에 걸친 대단지다. 단지명 기반 2차 조인은
대시보드 집계 단계에서 붙인다.

### scripts/build_dashboard.py

원본 + 단지 마스터를 PNU로 조인하고, 300세대 이상만 남겨 집계 JSON을 만든다.

## 저장 포맷

`data/trades/YYYY/YYYY-MM.csv.gz` 한 파일이 한 달치 서울+경기 전량이다.
월 약 17,000건, gzip 후 250KB 내외. 247개월 전체가 약 60~70MB.

### 결정론적 gzip

gzip은 헤더에 mtime을 기록하므로, 내용이 같아도 재생성하면 바이트가 달라져
git에 새 blob이 쌓인다. 매일 실행하면 히스토리가 계속 팽창한다.

따라서 **`mtime=0` 으로 고정하고 레코드 정렬 순서를 고정**한다.
내용이 바뀌지 않은 달은 바이트가 동일해 git이 아무것도 기록하지 않는다.
실제로 변하는 것은 최근 2~3개월(신고 지연·계약해제 반영)뿐이다.

정렬 키: `(sgg_cd, umd_nm, jibun, apt_name, area_sqm, floor, trade_date, price_10k)`

### CSV 컬럼

```
sgg_cd, umd_nm, jibun, apt_name, build_year, area_sqm, floor,
price_10k, trade_date, deal_type, seller_gbn, buyer_gbn,
land_leasehold, cdeal_type, cdeal_day
```

MCP 파서와 달리 **계약해제 건(`cdealType == "O"`)도 버리지 않고 플래그로 보존**한다.
해제 거래 자체가 대시보드에서 의미 있는 지표이기 때문이다.

원본은 대시보드가 직접 읽지 않으므로 `_config.yml` 의 `exclude` 에 넣어
Jekyll 빌드 산출물에서 제외한다. 사이트 용량에 영향이 없다.

## 체크포인트와 재개

`data/state/collect_state.json` 이 (시군구 × 월) 격자에서 어디까지 채웠는지 기록한다.

매일 실행 시 동작 순서:

1. 아직 채우지 못한 과거 칸을 오래된 것부터 채운다 (백필)
2. 최근 3개월은 매번 다시 받아 갱신한다 (신고 지연·계약해제 반영)
3. 일일 한도에 걸리면 그 지점을 저장하고 정상 종료한다 — 다음 날 이어서 진행

### 일일 한도 — 실측값 10,000콜

**실거래가 API 의 일일 한도는 10,000콜이고, 초과는 `resultCode` 가 아니라
HTTP 429 로 알려준다.** 2026-07-25 실측에서 성공 9,465콜(2006-01 ~ 2016-12) 직후
429 가 시작됐다. 앞선 시험 실행분까지 더하면 약 10,000 이다.

초기 구현은 `resultCode` 만 한도로 보고 4xx 는 재시도 불가 오류로 처리했다.
그 결과 한도에 닿고도 멈추지 않고 **8,319칸을 헛돌며 남은 예산을 전부 태웠다.**
HTTP 429 를 만나면 즉시 예산을 비우고 중단하도록 고쳤다.
(`tests/test_collector.py::TestQuotaSignal`)

cron 은 `MAX_CALLS=9000` 으로 여유를 둔다. 72개 시군구 기준 하루 125개월치다.

### odcloud 단지정보는 별도 한도

실거래가 한도가 소진된 상태에서 odcloud `AptIdInfoSvc` 는 정상 응답했다.
두 서비스의 한도는 분리되어 있어 같은 날 단지 마스터를 받을 수 있다.

## 오류 처리

| 상황 | 처리 |
|---|---|
| 네트워크 오류 / 5xx | 지수 백오프 3회 재시도 |
| `resultCode` 한도 초과 | 전체 중단, 체크포인트 저장 후 정상 종료 |
| 그 외 `resultCode != 000` | 해당 칸을 실패로 기록, 다음 칸 진행 (다음 날 재시도) |
| `totalCount > numOfRows` | 페이지를 끝까지 순회해 전량 확보 |

부분 실패한 달은 **체크포인트에 완료로 커밋하지 않는다.** 반쪽짜리 파일이
완료로 표시되는 것을 막기 위함이다.

## PNU 조인

실거래가 API는 `aptSeq` 를 제공하지 않지만 `sggCd`, `umdNm`, `jibun` 을 준다.
단지정보 API의 `pnu` 와 구조가 동일하므로 결정론적으로 조립할 수 있다.

```
PNU = 법정동코드(10) + 대장구분(1) + 본번(4) + 부번(4)

예) 대치동 1014-3
    1168010600 + 1 + 1014 + 0003 = 1168010600110140003
```

- 대장구분: 일반 지번 `1`, 산 번지 `2`
- 부번이 없으면 `0000`

단지명 퍼지매칭이 불필요해진다.

### umdNm 이 두 토큰으로 오는 경우

동 지역은 `역삼동` 처럼 한 토큰이지만 읍면 지역은 `고덕면 궁리` 처럼 두 토큰이다.
말단 토큰만 인덱스 키로 잡으면 2006-01 기준 5.6% 가 조인에 실패했다.
**시군구 아래 전체 접미사를 1차 키, 말단 토큰을 2차 폴백**으로 두어 해결했다.
말단 토큰이 같은 시군구 안에서 충돌하면(서로 다른 읍의 같은 리 이름) 모호한 것으로
보고 버린다. 틀린 PNU 를 만드는 것보다 조인 실패로 남기는 편이 낫다.

수정 후 2006-01 실측 **PNU 조립 성공률 100.00% (9,947/9,947)**.

### 조인 실패 대비

단지정보 API는 단지당 대표 PNU 하나만 반환한다. 여러 지번에 걸친 대단지는
일부 거래가 조인에 실패할 수 있다. (위 100% 는 PNU *조립* 성공률이고,
단지 마스터와의 *매칭률*은 별개다.)

1. 1차: PNU 완전 일치
2. 2차: (시군구 + 법정동 + 정규화된 단지명)
3. 그래도 미매칭인 건은 세대수 미상으로 남기고 대시보드에서 별도 집계

**매칭률을 로그로 남겨** 실제 커버리지를 확인할 수 있게 한다.

## 동시 요청

호출 하나에 2초 넘게 걸려 순차 실행이면 백필에 12시간이 든다.
월 안에서 시군구 단위로 `--workers` (기본 6) 만큼 병렬 호출해 약 13배 빨라진다.

예산 차감은 잠금으로 보호한다. 한 워커가 한도 초과를 만나면 남은 예산을 0 으로
비워 나머지 워커도 즉시 멈춘다.

## 상태 저장 시점

상태는 **월이 끝날 때마다** 저장한다. 실행 종료 시점에만 저장하면 cron 작업이
중간에 죽었을 때 그날 진행분 전체의 추적이 사라진다 (파일은 남지만 `done` 이 비어
다음 실행이 처음부터 다시 받는다).

호출 수는 월마다 기록한 뒤 마지막에 차액만 더해 이중 계상을 피한다.

## 구 신설 / 폐지 — 실측으로 해소됨

설계 초안에서는 화성시(2025년 4개 구 신설), 부천시(2016 폐지 / 2024 부활) 같은
행정구역 변경 때문에 과거 월은 상위 시 코드로 조회해야 한다고 봤다.
**실측 결과 그 반대였다.**

| LAWD_CD | 2006-01 | 2015-06 | 2026-06 |
|---|---|---|---|
| 41590 화성시 (상위) | 0 | 0 | 0 |
| 41597 동탄구 (하위) | — | 269 | 1,971 |
| 41190 부천시 (상위) | 0 | 0 | 0 |
| 41192 원미구 (하위) | — | 640 | 466 |

동탄구는 구 신설 10년 전인 2015-06 에도 269건을 돌려준다. 즉 API 가 과거 데이터를
**현재 행정구역으로 소급 재배치**하고 있다. 41110 수원시, 41130 성남시, 41170 안양시,
41270 안산시, 41280 고양시, 41460 용인시 상위 코드도 모두 2006년치까지 0건이다.

따라서 **현재 구 코드만 조회하면 되고 상위 시 코드는 조회 대상에서 제외**한다.
병행 조회와 그에 따른 중복 제거가 불필요해져 콜 수도 17,784 로 줄었다.

이 결론은 `tests/test_collector.py::TestRegionTable` 이 지킨다.

## 검증

수집기는 순수 함수(XML 파싱, PNU 조립, 체크포인트 전이)와 I/O를 분리한다.

- XML 파서: 저장해 둔 실제 응답 샘플로 검증
- PNU 조립: 산 번지(대장구분 2), 부번 없는 지번, 본번 4자리 초과 등 엣지케이스
- 체크포인트 재개: 합성 상태로 전이 검증
- 결정론적 gzip: 같은 입력을 두 번 써서 바이트가 동일한지 확인

## 진행 상황 (2026-07-25 기준)

- 실거래가: **9,465 / 17,784 칸 (53.2%)**, 2006-01 ~ 2016-12, 132개 파일 27MB
- 단지 마스터: 완료 (72/72 시군구, 187,208건)
- 남은 백필: 2017-01 ~ 2026-07 (약 8,300콜). 하루 9,000콜 예산이면 **다음 실행 1회로 완료**
- cron: 매일 04:30, `MAX_CALLS=9000 AUTO_COMMIT=1 AUTO_PUSH=1`

백필이 끝나면 수집기는 자동으로 갱신 모드(최근 3개월 재수집, 하루 216콜)로 전환된다.
